# Задачи и сообщения коммитов

Общий вход для всех чатов и направлений — [project-roadmap.md](project-roadmap.md).
Core/ECS/Render, Editor, runtime и инструменты используют одну доску и одни milestones.
Компонент отмечается area:core/area:render/area:editor/area:tooling и другими метками;
задача может затрагивать несколько областей. До изменения общего API фиксируем
контракт, потребителей и связанные Issues. В активной Issue сохраняем ведущего,
границы работы, ветку/commit/PR, результаты и следующий шаг для продолжения из другого чата.

## Нумерация

Постоянный ID задачи: `ОБЛАСТЬ-NN`, например `LOAD-01` или `PROCESS-01`.
Область — заглавные латинские буквы/цифры, начинается с буквы.
Номер — положительное число минимум из двух цифр: 01, 02, …, 99, 100.
Номер увеличивается внутри области; закрытые ID не переиспользуются и
не меняются при переносе задачи между этапами/релизами.

Реестр ID и кратких названий — [.github/tasks.json](../.github/tasks.json).
Перед началом новой задачи добавить следующий свободный номер в её области.
При параллельной работе сначала зарезервировать ID в общей ветке/Issue,
чтобы два исполнителя не выбрали один номер. Смена названия не меняет ID.

GitHub Issue имеет свой номер `#N`, который назначает GitHub. Он не заменяет
ID проекта: заголовок Issue — `[LOAD-01] Надёжная загрузка сцен`,
а ветка может называться `codex/load-01-load-errors`.
Большую задачу делить на самостоятельные Issue с новыми ID и ссылкой на родителя;
не вводить дополнительные форматы наподобие LOAD-01.1.

## Доска

[Публичная доска robot2D — Development](https://github.com/users/Enziferum/projects/5)
связана с репозиторием Enziferum/robot2D. Статусы: Backlog, Ready, In Progress, Review, Done.
Отложенные задачи остаются в Backlog с причиной. Блокировку отмечаем отдельно,
с описанием необходимого решения. Review означает, что реализация готова,
но остаются проверки; Done — критерии задачи выполнены.

В Issue записывать цель, границы работы, критерии готовности, ответственность,
результаты автоматических/ручных проверок и PR. Реализованный локально код
не означает, что он опубликован или прошёл удалённый CI.
CancellationToken и Snapshot остаются за пользователем.

Релизные цели и зависимости — [release-roadmap.md](release-roadmap.md).
Релизы 0.8.0/0.9.0/1.0.0 обозначаются Milestone, а не отдельными досками.
`owner:shared` означает совместную задачу без заранее выбранного ведущего:
перед стартом пользователь выбирает собственную реализацию с помощью ассистента
или реализацию ассистентом. Сложные задачи движка доступны обоим участникам.
`owner:user` закрепляет реализацию Snapshot/CancellationToken за пользователем.
В Issue фиксируем ведущего и формат помощи: проектирование/подсказки, ревью,
проверки либо реализация. Выбор помощи/ревью не разрешает ассистенту забрать код.
Assignees содержит реальные аккаунты GitHub; фиктивного исполнителя Codex не назначаем.

Оперативные статусы ведём в GitHub Projects и Issues. editor-roadmap.md сохраняет
план, архитектурный контекст и датированные результаты проверок; при расхождении
сначала сверить историю Issue и актуальный код. Соответствие ID → номер Issue
записано в github.issues файла .github/tasks.json; статусы в этот реестр не дублируем.

## Работа с GitHub через CLI

По требованию пользователя создание/изменение Issues и Projects выполняется
через `gh`, без автоматизации браузера. Для нового рабочего места установить
[GitHub CLI](https://cli.github.com/), затем выполнить:

```text
gh auth login --hostname github.com --git-protocol https --web --scopes project
```

Здесь браузер используется только для подтверждения входа gh. Доступ плагина
и авторизация браузера не заменяют авторизацию CLI. Не присылать токены в чат.
Локально 2026-10-15 gh 2.102.0 установлен в игнорируемом work/github-cli/bin/gh.exe;
его можно вызывать по этому пути, если gh отсутствует в PATH.

Перед созданием проверить реестр и Issues, включая закрытые:

```text
gh issue list --repo Enziferum/robot2D --state all --limit 100 --json number,title,state,url
gh project item-list 5 --owner Enziferum --limit 100 --format json
```

При росте списка учитывать limit и пагинацию; отсутствие задачи в усечённой
выдаче не доказывает, что её нет. У Issue должен быть один постоянный ID.
Новую задачу сначала зарегистрировать, затем создать Issue с телом из UTF-8 файла:

```text
gh issue create --repo Enziferum/robot2D --title "[LOAD-02] Название новой задачи" --body-file work/issue-body.md
```

После создания записать фактический номер в github.issues и добавить **возвращённый
URL** на доску. Для существующей LOAD-01 пример смены статуса (gh 2.102.0):

```text
gh project item-add 5 --owner Enziferum --url https://github.com/Enziferum/robot2D/issues/45
gh project item-edit 5 --owner Enziferum --url https://github.com/Enziferum/robot2D/issues/45 --field Status --value "In Progress"
```

Не считать Issue добавленным/перемещённым только по попытке команды:
повторно прочитать project item-list и проверить URL, Status, отсутствие дубликатов.
Для старого gh без --field/--value использовать field-list и GraphQL node IDs
в item-edit либо обновить CLI.

## Ветки и метки задач

Одна рабочая ветка относится к одной основной задаче. Формат имени:
`TASK-ID`, например `ASSET-02` (уточнение пользователя 2026-10-16: без
префикса `codex/`). Ветку создаём только при начале работы.
Базовую удалённую ветку указываем явно; основная интеграционная ветка — `dev`.
2026-10-15 `october2026_dev` слита в `dev` через PR #43 merge-коммитом e54408f.
Новые задачи начинаются от актуального `dev`, а их PR направляются в `dev`.
Старые записи с october2026_dev ниже сохраняют историческую базу прошлых задач.
Если локальные изменения базы не опубликованы, сначала согласовать их публикацию:
gh создаёт ветку от удалённого состояния, а не от локальных незакоммиченных файлов.

При параллельной работе Codex выполняет порученную реализацию фоново в отдельном
Git worktree и ветке `TASK-ID` от актуального удалённого `dev`. Перед созданием
проверяет существующие worktrees и связанные ветки и переиспользует подходящие.
Основной checkout пользователя под IDE не переключает, его исходники, индекс и
конфигурацию сборки не меняет. Сборка и проверки выполняются в worktree задачи,
публикация — через PR в `dev`; обычные шаги согласованной реализации не требуют
повторного согласования, но ограничения среды на выполнение команд сохраняются.

Создавать ветку через gh issue develop: это регистрирует связь в Development Issue.
Пример для PROCESS-01 (#44):

```text
gh issue develop 44 --repo Enziferum/robot2D --list
gh issue develop 44 --repo Enziferum/robot2D --base dev --name PROCESS-01
gh issue develop 44 --repo Enziferum/robot2D --list
```

Сначала проверить существующие связанные ветки и удалённую базу. Команда без
--checkout не переключает локальную рабочую папку; для переключения выполнить
отдельно git fetch / git switch после проверки незавершённых изменений.
Само имя ветки не создаёт связи на GitHub. В описании PR также указывать Issue;
Closes #N использовать, только когда PR действительно завершает задачу.

Для готового шага незавершённой задачи использовать Refs #N и явно перечислить
оставшуюся работу. Merge такого шага не закрывает Issue автоматически.

2026-10-15 создана и проверена связанная ветка `codex/process-01-task-workflow`
для PROCESS-01 (#44) от october2026_dev, SHA eff6c08.
Локальный origin использует SSH: при отсутствии SSH-доступа gh issue develop
может создать ветку/связь на сервере и затем завершиться ошибкой локального fetch.
В этом случае сначала проверить --list и удалённую ветку, не повторять создание
вслепую. Git remote автоматически не менять. Локальный checkout — отдельное действие.

Метки Issues: `area:editor`, `area:tooling`, `area:workflow` и `type:*`
(bug, feature, refactor, maintenance, design, tests). Прогресс отражается в
Status доски. Определения и назначения — `.github/task-labels.json`.
ID уже присутствует в заголовке Issue; отдельная метка для каждого ID не требуется.

```text
pwsh -File scripts/sync_task_labels.ps1
pwsh -File scripts/sync_task_labels.ps1 -Apply
```

Без -Apply команда показывает план. При применении создаются отсутствующие метки
и добавляются назначения существующим Issues после проверки их ID. Прочие метки,
их цвет и описание сохраняются. После применения проверить список Issues через gh.

## Сообщения коммитов

Правила общей версии core/editor, dev-сборок, тегов релизов и версий файлов
зафиксированы в [versioning.md](versioning.md). ID задачи и номер версии
приложения имеют независимые назначения.

Первая строка обязательна в формате `TASK-ID: описание`:

```text
LOAD-01: Сохранять текущую сцену при ошибке загрузки
PROCESS-01: Проверять ID задачи перед коммитом
```

ID должен существовать в .github/tasks.json; описание не может быть пустым.
Для нескольких задач выбрать основную, остальные указать в теле сообщения.
Не помещать перед ID тип изменения, fixup! или другой текст.
Автоматические merge/revert-сообщения также требуют ID:
например, использовать merge --no-commit / revert --no-commit и затем commit
с сообщением установленного формата. Изменение сообщения amend тоже проверяется.
Наличие ID не доказывает соответствие содержимого задаче — это проверяет ревью.

## Установка hook

После clone из корня репозитория выполнить (Python 3.8+):

```text
python scripts/install_git_hooks.py
```

Скрипт локально устанавливает core.hooksPath=.githooks. Он не перезаписывает
другой hooksPath: если уже подключён менеджер hooks, вручную добавить вызов
scripts/check_commit_message.py с путём к файлу сообщения в существующий commit-msg,
а scripts/pre_commit.py — в существующий pre-commit.
На Linux/macOS для hook нужен executable bit; установщик задаёт его.
Git для Windows запускает shell-hook через собственный sh, Python нужен в PATH.
Hooks не включаются автоматически при clone, каждый участник выполняет установку.

Проверить без создания коммита:

```text
git hook run commit-msg -- путь-к-файлу-сообщения
python -m unittest discover -s scripts/tests -v
```

Hook блокирует commit при неправильном сообщении; сообщения он не переписывает.
Проверка локальная: Git допускает --no-verify, поэтому это не серверный запрет.
TOOL-01 добавляет pre-commit: форматирование, сборку, headless-тесты и строгий
clang-tidy собственного кода. Установка инструментов, локальные параметры,
правила staged-файлов и ручной запуск описаны в
[инструкции](development-tools.md#обязательный-pre-commit).
Текущий CI продолжает проверять сборку/тесты и регрессии scripts/tests.
