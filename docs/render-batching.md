# Корректность существующего batching

Этап RENDER-02, 2026-10-15. Исправления относятся к существующему API
RenderTarget/RenderWindow; новый контракт проходов и команд ещё не согласован.

## Ёмкость и выполнение

Один GPU batch в OpenGLRender вмещает 20000 quad: 80000 вершин и 120000 индексов.
CPU-буфер и VBO выделяются на полное число вершин; IBO — на число индексов,
умноженное на sizeof(uint32_t). Аргумент размера IndexBuffer::Create — байты.
Та же ошибка размера IBO исправлена в публичном QuadBatchRender, используемом
текстом. Его собственный лимит 1000 quad и механизм заполнения здесь не менялись.

При исчерпании вершин или texture slots завершённый batch сохраняет свои вершины
и таблицу texture ID на CPU. Новый batch начинает заполнение с начала рабочего
буфера; слот 0 зарезервирован, пользовательские текстуры занимают слоты 1–15.
Переполнение не вызывает beforeRender/afterRender и не сбрасывает статистику
или данные других слоёв.

afterRender выполняет все существующие слои по возрастанию ID. В каждом слое
последовательно исполняются сохранённые batch, текущий batch и cache VertexArray.
Это сохраняет порядок слоёв даже при подаче переполненного верхнего слоя раньше
нижнего. Немедленное рисование верхнего слоя при переполнении нарушало бы порядок.

Стоимость решения — дополнительная CPU-память пропорционально объёму сохранённых
batch до flush/afterRender. GPU-буферы остаются фиксированного размера.
Это исправление корректности, без настройки общего лимита памяти или оптимизации
загрузок GPU; их обсуждаем вместе с будущим контрактом рендера.

flushRender(layer) самостоятельно загружает и рисует все pending/current batch
этого слоя, выполняет его VertexArray cache и сбрасывает указатели/счётчики.
Повторный flush или afterRender без новых данных не перерисовывает старые quad.
Пустые quad-batch не создают draw calls; cache без quad всё равно выполняется.
Неверный ID явного flush отклоняется с диагностикой.

Явный flush остаётся немедленной операцией: вызывающий код отвечает за порядок
между вручную выполненными слоями и последующей отрисовкой. Автоматический
порядок всех накопленных слоёв гарантируется при штатном afterRender.

beforeRender сбрасывает статистику и накопленные команды для нового цикла.
drawQuads/drawVertices учитывают поданные quad и их вершины, включая находящиеся
за экраном. drawCalls учитывает исполненные GPU draw calls, включая VertexArray
и прямой draw3D. Это статистика одного цикла beforeRender, не всех viewport кадра.

Путь quad принимает ровно четыре вершины; неверный размер отклоняется с логом
также в Release. Обобщение примитивов относится к будущему контракту.

## Владение ресурсами слоя

Внутренний RenderLayer больше не копируется; рабочий CPU-буфер и белая текстура
перемещаются с единственным владельцем. Это исправляет удаление texture ID при
размещении временного слоя в vector и при его последующих перевыделениях.
Ранее удалённый ID мог быть переиспользован framebuffer-текстурой; создание
следующего слоя удаляло её через устаревшую копию и делало framebuffer неполным.
Публичные правила копирования Texture/ShaderHandler этим шагом не менялись.

Для OpenGL 4.3 также исправлен target двух glTexParameteri в Texture::setupGL:
передаётся GL_TEXTURE_2D, а не ID текстуры.

## Проверки

Постоянные сценарии — editor/tests/BatchRenderTests.cpp, часть
robot2D-editor-test-suite, связаны только с core. Включение:
RB2D_BUILD_EDITOR_TESTS=ON и RB2D_EDITOR_GRAPHICS_TESTS=ON.

```text
cmake --build <build-dir> --target robot2D robot2D-editor-test-suite -j 4
ctest --test-dir <build-dir> -R core-batch- --output-on-failure --no-tests=error
```

Семь сценариев зарегистрированы отдельно для путей OpenGL 4.3 и 4.5.
Каждый процесс создаёт скрытый debug context и RGBA8 framebuffer 64×64;
проверяет пиксели, статистику и отсутствие GL errors. Наличие контекста только
более новой версии драйвера не означает проверку на драйвере, ограниченном 4.3.
Отсутствие запрошенного контекста возвращает Skipped (77), а не успех.

- capacity: 5001, 20000, 20001 и 40001 quad, пиксели контрольных элементов до/после
  старых и новых границ ёмкости, суммарная статистика, повторный afterRender;
- textures: первая текстура, 31 уникальная текстура, повторное использование,
  переполнение слотов и обратный порядок текстур в следующем кадре;
- layers: все пять слоёв, переполнение верхнего слоя до подачи нижнего,
  переполнение обоих слоёв, новый пустой кадр;
- flush: пустой кадр, прозрачное наложение с промежуточным и повторным flush,
  явный flush накопленных batch и добавление данных после него;
- geometry: 1000 quad через QuadBatchRender/VertexArray, корректный размер IBO,
  cache слоя без quad и отсутствие повторного выполнения cache;
- three-d: базовое рисование VertexArray через существующий draw3D с собственной
  программой и установкой 3D view; полноценные 3D-сцены и depth этим не покрыты;
- malformed: 0/3/5 вершин и неверный слой flush, диагностирование отказа,
  отсутствие рисования и работоспособность следующей корректной команды.

Локально Windows/GCC 16.2/Ninja Release: редактор и suite собраны; 60/60 CTest
без пропусков, включая все 14 batch-сценариев. Удалённый CI, Linux и интерактивный
Editor для этих изменений ещё не запускались. В CI сценарии входят в существующий
Linux graphics-запуск; Windows graphics проверяются локально.

## RENDER-03: смешанный порядок внутри слоя, 2026-10-15

Первый шаг [RENDER-03 #82](https://github.com/Enziferum/robot2D/issues/82):
ветка `codex/render-03-order-camera` от `dev` @ `9f131c5`, отдельный worktree.
Публичный API RenderTarget/RenderStates и контракт нового рендера не меняются.

При подаче VertexArray backend завершает предыдущую группу quad на CPU и
запоминает позицию геометрии между группами. Flush выполняет их в исходном
порядке: sprite → atlas/text VertexArray → sprite. Переполнение буфера или
слотов текстур не перемещает геометрию в конец слоя. Между слоями сохраняется
порядок layerID; геометрия не вызывает раннее рисование верхнего слоя.
Последняя группа quad рисуется напрямую из CPU буфера, без дополнительного
копирования для обычного кадра только из quad. Повторный flush не рисует
выполненные команды; несколько VertexArray подряд сохраняют порядок.

Владение ресурсами осталось прежним: GPU-данные, shader и texture должны жить
и сохранять нужное содержимое до flush. Изменение uniform или VBO после подачи
не фиксируется новым механизмом; такой контракт относится к RENDER-04/05.

Добавлены `core-batch-mixed-43/45` и `core-batch-mixed-overflow-43/45`.
Они проверяют полупрозрачные quad, геометрию с текстовым RED-атласом, следующий
quad, два VertexArray подряд, явный/повторный flush, новый кадр, 20001 quad,
позднюю подачу нижнего слоя и верхний HUD. Проверяются GL errors и журнал GL.
Это проверка пути atlas/text VertexArray; настоящий UI и Core Text с
пользовательским шрифтом ими не объявляются проверенными.

До исправления все 4 новых случая воспроизводимо падали: например, вместо
RGB (32, 64, 128) получалось (32, 128, 64). После исправления проходят все
18 batch-сценариев. Windows / GCC 16.2 / отдельный Ninja Release:
собраны robot2D, robot2D-core-tests и robot2D-editor-test-suite; CTest 70/70
без пропусков. Исходники checkout пользователя и его build-каталоги не менялись.

RENDER-03 остаётся открытой: камера и resize/viewport — следующий шаг;
реальная игровая/UI-приёмка ещё нужна. RENDER-04/05 и 3D redesign не реализованы.


## RENDER-03: камера и resize/viewport, 2026-10-16

Продолжение в той же ветке от dev и PR #107: предыдущий коммит 42f4444 ещё
не слит; его Windows/Linux CI проверен и прошёл. Новый публичный API target,
очереди или материалов не вводится. Добавлен только внутренний RenderImpl::setSize
для уведомлений уже существующего RenderWindow::resize/onResize.

Смена 2D-камеры, raw/3D projection или виртуального viewport завершает все
накопленные слои с прежними параметрами до изменения shader/viewport.
Это граница участка отрисовки: внутри участка сохраняется порядок layerID;
следующий участок рисуется после предыдущего. Повторная установка той же
2D-камеры и того же виртуального размера не разбивает batch. Произвольная
мутация shader uniforms/VBO вне этих методов по-прежнему остаётся
ответственностью вызывающего кода до flush (дальнейший контракт — RENDER-04/05).

Flush применяет сохранённые размеры viewport текущего участка, затем
восстанавливает внешний GL viewport. Это учитывает GLFW, который может поменять
GL viewport раньше доставки логического resize. Нормализованный View::viewport
используется и при рисовании слоя, и в mapPixelToCoords. Последний учитывает
letterbox и преобразование верхнего/нижнего начала координат. Состояние виртуального
viewport хранится в экземпляре backend, а не в общей глобальной переменной.

RenderWindow передаёт положительные resize в backend: обновляются размер,
default view и слои без явно установленной камеры. Явно заданная камера
сохраняется, даже если при установке совпадала с default view. Нулевой/отрицательный resize не создаёт некорректной проекции:
остаётся последний положительный размер. Очень маленький положительный
виртуальный размер использует доступную область без отрицательных отступов.

beforeRender принимает viewport уже привязанного framebuffer, как в Editor.
Само пересоздание FrameBuffer или ручная смена OpenGL framebuffer не откладывается
этим кодом: вызывающий завершает накопленную отрисовку до удаления/замены target.
Текущий Editor делает afterRender до UI, где Viewport/GameViewport меняют FBO.
Общий механизм отложенных target/pass и владения framebuffer относится к RENDER-04/05.

В Editor runtime-камера выбирается до обхода Drawable в z-order. Раньше она
применялась в момент встречи сущности камеры, поэтому после введения границы
старые спрайты могли оставаться с editor-проекцией. Исправлен именно этот
потребитель; правила ECS, жизненный цикл runtime и C# API не менялись.

Новые сценарии `core-batch-camera-43/45`, `core-batch-viewport-resize-43/45`,
`core-batch-window-resize-43/45` и `editor-scene-runtime-camera-order`
воспроизвели дефекты до исправлений. Покрыты старые/новые пиксели камеры и
viewport, общий текстовый shader, raw projection, половина viewport, letterbox,
преобразование координат, одинаковые параметры без лишнего flush, нулевой и
минимальный размер, неверный layerID, изоляция двух RenderTarget, скрытый
RenderWindow и камера после спрайта в z-order. Проверяются GL errors.
После исправлений прошли все 24 batch-сценария и полный CTest 77/77 без пропусков;
robot2D, robot2D-core-tests и editor-test-suite собраны в отдельном Ninja Release,
Windows/GCC 16.2. Это результаты нового запуска, не повторное заявление о старых проверках.

Ручная приёмка: сцена со sprite/text/sprite и полупрозрачным HUD; перемещать
камеру, менять размер Scene/Game View, окно и сворачивать/восстанавливать его.
Проверить порядок, отсутствие скачков старой геометрии и совпадение координат
курсора с изображением после letterbox. Повторить с камерой после спрайтов
в z-order. Интерактивная проверка ещё не выполнена; RENDER-03 не объявляется Done.


Дополнительная проверка минимизации: нулевой GL viewport от GLFW также
не заменяет сохранённый положительный viewport в следующем beforeRender.
Проверяется преобразование координат без NaN после уведомления 0x0 и
нулевого GL viewport. Для resize различаются слои с default view и явно
заданной камерой, даже когда их размеры изначально совпадали.
