# Физика 2D и события контактов

Живая документация для разработчиков robot2D и основа будущего учебника.
Версия библиотеки: **Box2D 2.4.1**; API других версий сюда автоматически не переносим.
PHYS-01, первый шаг от `dev` @ `c05a55b`, 2026-10-16.
Задача: [#78](https://github.com/Enziferum/robot2D/issues/78).

## Как читать и расширять этот документ

Начни с устройства мира и пяти опытов ниже, затем переходи к контрактам адаптера.
Разделы «Текущий контракт» описывают проверенный код; «Предложение» не обещает
готовый API. Каждый новый физический API дополняем единицами, владельцем данных,
допустимой фазой вызова, примером и ссылкой на регрессию. Ручные опыты не объявляем
пройденными по автоматическим тестам. Историю выполнения храним в Issue/roadmap;
этот документ объясняет действующий интерфейс и его причины.

## Устройство мира Box2D

| Объект | Ответственность | Пример |
|---|---|---|
| World | Владеет физическими объектами и выполняет Step | Арена |
| Body | Положение, угол, скорости, масса и движение | Тело игрока |
| Shape | Геометрия в локальных координатах тела | Прямоугольник или круг |
| Fixture | Прикрепляет форму к телу; материал, sensor, фильтры | Коллайдер игрока |
| Contact | Взаимодействие двух фикстур | Игрок касается стены |
| Joint | Ограничение относительного движения тел | Дверь на петле |

Спрайты, здоровье и команды управления не являются понятиями Box2D.
Тело может двигаться без фикстуры, но тогда у него нет формы для столкновений.
Box2D допускает несколько фикстур на теле: например, корпус и сенсор ног.
В текущем адаптере robot2D на сущность создаётся одно тело и максимум одна Box-фикстура.
Наличие enum Circle в компоненте ещё не означает реализацию круглого коллайдера.
См. [fixture](https://box2d.org/doc_version_2_4/classb2_fixture.html).

| Тип тела | Движение и реакция | Игровой пример |
|---|---|---|
| Static | Симуляция не двигает; столкновения не сдвигают | Стена |
| Dynamic | Действуют силы, импульсы и разрешение столкновений | Игрок, ящик, враг |
| Kinematic | Движется по заданной скорости, силы не меняют движение | Управляемая платформа |

В Box2D 2.4 Kinematic не сталкивается со Static и другими Kinematic.
Для автоматического упора игрока в статические стены используй Dynamic.
Sensor тоже подчиняется этим ограничениям: пересечение двух Static сенсоров
само по себе не даст нужного контакта.
[Типы тел и CCD](https://box2d.org/doc_version_2_4/md__e_1_2github_2box2d__24_2docs_2dynamics.html).

## Единицы и способы управления

Box2D использует метры, килограммы, секунды и радианы; движок переводит
пиксели в метры при создании тела. Скорость 4 m/s при 32 px/m означает 128 px/s.
Скорость **не умножают на dt перед SetLinearVelocity**: интеграцию делает Step.
[Единицы библиотеки](https://box2d.org/doc_version_2_4/).

| Управление | Смысл | Применение |
|---|---|---|
| SetLinearVelocity / C# LinearVelocity | Непосредственно задать скорость | Отзывчивое управление |
| ApplyForceToCenter / C# AddForce | Разгонять силой в течение шага | Двигатель, ветер |
| ApplyLinearImpulse / C# ApplyLinearImpulse | Однократное изменение движения | Толчок, отдача |

Приближённо `a = F / m`, а для импульса `deltaV = J / m`.
Импульс в центр не добавляет вращение; вне центра может добавлять его.
Силу для непрерывного воздействия прикладывают на каждом физическом шаге,
импульс события — один раз. Не надо дополнительно умножать импульс на dt.
[Управление телом](https://box2d.org/doc_version_2_4/classb2_body.html).

Прямая запись Transform у Dynamic не является текущим API телепортации:
следующий physics update вернёт координаты физического тела. Для движения
задавай скорость/импульс. Нативный SetTransform годится для явного переноса,
но не заменяет обычное движение через столкновения.

В robot2D позиция Transform — пиксели, LinearVelocity — m/s, импульс — kg*m/s.
Перегрузка C# ApplyLinearImpulse с worldPosition сейчас передаёт точку напрямую
в Box2D: она ожидает **метры**, не пиксели Transform. Это неоднородность API.
AddForce объявлен в C#, но при сверке найдено различие имён internal call:
`Rigidbody2DComponent_AddForce` против регистрации `RigidBody2DComponent_AddForce`.
Его рабочий сквозной путь этим PR не проверен; опыт ниже использует скорость
и импульс. Исправление AddForce следует сделать отдельным шагом с регрессией.

## Шаг симуляции: текущий контракт и дальнейшее согласование

Fixed timestep означает длительность одного шага, например 1/60 секунды;
timestamp означает отметку времени. Это разные понятия; отдельный тип/API
fixedTimestamp в текущей интеграции физики не вводится.

Адаптер делает один `b2World::Step(dt, 6, 2)` с полученным dt. Числа 6 и 2 —
итерации решения скоростных и позиционных ограничений, не число кадров.
Step выполняет обнаружение контактов, интеграцию и решение ограничений.
[World::Step](https://box2d.org/doc_version_2_4/classb2_world.html).

**Текущий Engine уже имеет фиксированный накопитель** `timeProcessed`:
шаг `1 / EngineConfiguration::maxFrameRate`; update вызывается ноль или
несколько раз за внешний кадр. Имя maxFrameRate не означает отдельный
ограничитель render FPS. В runtime текущий порядок:

```text
Engine: накопить прошедшее время
  для каждого накопившегося фиксированного шага:
    Application::update(fixedDt)
      Scene::updateRuntime(fixedDt)
        C# OnUpdate(fixedDt)
        Box2D Step(fixedDt)
        синхронизация Transform и доставка физических событий
        runtime systems
  GUI / render
```

Исходники: [Engine.cpp](../core/src/Engine.cpp), [Scene.cpp](../editor/src/Scene.cpp).
Самостоятельного накопителя внутри адаптера нет; это не означает, что обычный
runtime получает переменный шаг. Тесты адаптера передают dt явно.

Сверка с Core-чатом «Составить план ревью Core/Util», 2026-10-16:
отдельных OnFixedUpdate, frame-update API, интерполяции и timeScale нет.
Не выделена независимая частота физики; не ограничены накопленное время и число
догоняющих шагов. Play/Stop существуют, полноценная политика Pause/Resume не готова.

В [CORE-02 / PR #122](https://github.com/Enziferum/robot2D/pull/122) предложенный
вариант доставки FIFO событий до updates уже реализован в отдельной ветке,
но на момент сверки PR draft и в базу PHYS-01 не входит. Контракт ввода —
[core-events.md ветки CORE-02](https://github.com/Enziferum/robot2D/blob/CORE-02/docs/core-events.md),
оставшаяся интеграция — [INPUT-01 #79](https://github.com/Enziferum/robot2D/issues/79).
Нажатие между шагами нельзя терять или повторять на каждом догоняющем tick.

**Предложение для следующего согласования**, не готовый интерфейс:
подготовка ввода tick → OnFixedUpdate(fixedDt) → один Step(fixedDt) →
синхронизация/события. Одного владельца накопителя достаточно: второй независимый
цикл внутри адаптера потребует другой семантики команд и событий.
Нужно отдельно выбрать fixedDt, предел догоняющих шагов и судьбу лишнего времени,
поведение Pause/Play/Stop и потребление input edges. Перенос нынешнего OnUpdate
на render-частоту будет изменением поведения существующих скриптов.

## Геометрия и параметры

`Box2DPhysicsAdapter` владеет миром, телами и фикстурами. Одной сущности
соответствуют одно тело и не более одной прямоугольной фикстуры; дети обходятся
рекурсивно. Повторный `addRuntime` не создаёт дубликаты.

Координаты Transform и offset коллайдера заданы в пикселях, масштаб — 32 px/m.
`Collider2DComponent::size` задаёт долю размера Transform для **полуразмера**:
значение `(0.5, 0.5)` даёт прямоугольник полного размера Transform.
Локальный центр равен `size * (0.5 - origin) + offset`; размеры и центр
переводятся в метры. Transform хранит угол в градусах, Box2D — в радианах.
После Step угол присваивается абсолютно, без накопления.

Учитываются Static/Dynamic/Kinematic, fixedRotation, bullet, gravityScale,
linear/angular damping, density, friction, restitution и restitutionThreshold.
Невалидные параметры тела/геометрии отклоняются с UUID и причиной в журнале.
Неположительный или нечисловой dt не запускает Step.

Матрица слоёв разрешает Player/Enemy взаимодействовать с Ground/Wall,
Projectile — с Enemy/Wall/Ground. Trigger взаимодействует с Player/Enemy/Projectile;
для событий нужен `isTrigger=true`. Player/Projectile по умолчанию исключены.
При `useDefaultMask=false` используется собственная маска; `markFilterDirty`
применяет обновлённые category/mask/group к фикстуре перед следующим Step.

## Доставка событий

- На одну пару фикстур: один Enter при начале контакта, затем один Stay на
  каждый последующий Step и один Exit при завершении. Спящие контакты и сенсоры
  сохраняют Stay. Повторное касание после Exit начинает новую пару событий.
- Доставка выполняется после Box2D Step, когда мир разблокирован, отдельно
  каждому живому участнику: `callback(contact, self, other)`.
- Порядок A/B канонический по UUID; нормаль направлена A → B. C# получает
  `normalToMe`: для A — отрицательную нормаль, для B — положительную.
- Идентификаторы фикстур ненулевые, уникальны в пределах запущенного мира
  и стабильны до удаления фикстуры. Они не являются указателями или сохранёнными ID.
- Точки контакта и separation заданы в метрах, импульсы — в единицах Box2D.
  Сенсоры не имеют manifold: pointCount, точки и нормаль нулевые.
  Exit не содержит актуальных точек/импульсов; нормаль сохраняется из контакта.
- Native/managed ABI остаётся прежним: Pack=1, PhysicsContact2D — 84 байта,
  PhysicsContactPoint2D — 12 байт, enum — byte, bool — I1.
  Пакет копируется для каждого C# получателя, поэтому изменение `ref` локально.
  Каждый ScriptInstance имеет собственный MonoClassWrapper/объект даже для одного класса.
- Числовой ABI enum задан явно: Enter=0, Stay=1, Exit=2, EnterTrigger=3,
  ExitTrigger=4, StayTrigger=5. Порядок строк enum не должен менять эти значения.
  После исправления рассогласования нужно пересобрать ScriptCore и скрипты проекта:
  C# может встраивать числовые значения enum в уже собранные DLL.

Урон от одного касания следует наносить в Enter, а не Stay. Удаление/пометка
тела на удаление подавляет оставшиеся Enter/Stay с ним в текущей доставке.
Исключение C# обработчика регистрируется с участниками и типом события.

## Создание, удаление и Stop

`addRuntime`/`removeRuntime` из callback ставятся в очередь и применяются после
доставки событий. Remove имеет приоритет перед Add той же сущности в одном пакете.
Вне callback операции выполняются сразу. Удаляется также физическое поддерево;
у оставшегося участника контакта будет один Exit на следующем Step.
`Scene::processRemovals(Runtime)` снимает тела до удаления сущностей из ECS.
Это контракт удаления физики, а не новый API создания/удаления C# объектов.

Stop из callback прекращает дальнейшую доставку и освобождает мир после выхода
из callback. Stop/деструктор очищают runtimeBody/runtimeFixture всех ещё доступных
компонентов, контакты, очереди и callback. Повторный Stop безопасен.
Вложенный update игнорируется, Start из callback отклоняется с диагностикой.

Сцены сохраняют IsTrigger, CategoryBits/MaskBits/GroupIndex, GravityScale,
LinearDamping и AngularDamping. Поля опциональны при чтении старых сцен;
версия схемы не повышается. Файлы пользовательских проектов этот шаг не меняет.

## Проверка и границы

Постоянные `editor-physics-*`: geometry, walls, bullet, triggers, filters,
lifecycle, callbacks, invalid, serialization, managed. Последний сценарий
загружает свежую ScriptCore и PhysicsDriver через настоящий ScriptEngine/Mono:
два экземпляра одного класса, ABI, Enter/Stay/Exit, направления нормалей
и изоляция ref-пакетов. Для триггеров проверяются оба C# получателя: Enter,
несколько Stay, Exit, отсутствие лишних вызовов после выхода, повторный полный
цикл и Stop. Проверяются счётчики, порядок фаз и тип/метаданные пакета.
Регрессия воспроизвела падение до согласования enum, затем прошла после фикса. Все сценарии доступны в обычной headless suite.

На Windows/Release в `work/phys-01-build` собраны редактор, core-tests и
editor-test-suite; прошли 103/103 CTest, включая 41 graphics и 10 новых physics.
Полный обязательный hook дополнительно проверяет формат и строгий clang-tidy.

Ручная приёмка: в тестовой игровой сцене поставить статические стены, Dynamic
Player/Enemy, Projectile с bullet и сенсор Trigger. Проверить остановку у стен,
один урон на Enter, trigger callbacks, удаление пули и два цикла Play/Stop.
Эта интерактивная приёмка и standalone ещё не выполнены.

Полный путь C# Instantiate/Destroy и его lifecycle остаётся в
[RUNTIME-01 #77](https://github.com/Enziferum/robot2D/issues/77); поэтому PHYS-01
не закрывается этим шагом. Нет новой реализации one-way/drop-through,
круглых коллайдеров, отдельного physics scheduler или переработки Core ECS.


## Практикум: пять небольших опытов

Это инструкция для ручного разбора в новой тестовой сцене. Пользовательские
проекты автоматически не менялись, интерактивный практикум ещё не выполнен.
Перед каждым опытом нажимай Stop и возвращай исходные условия.
Для каждого шага сначала предскажи результат, затем сравни наблюдение с ожиданием.

### Подготовка

Создай тестовую сцену с камерой, видящую область примерно 0..320 × 0..200 px.
Добавь два видимых объекта с origin=(0,0), нулевым углом и BoxCollider size=(0.5,0.5), offset=(0,0):

| Объект | Position px | Size px | Body | Layer |
|---|---|---|---|---|
| Mover | (0,64) | (32,32) | Dynamic | Player |
| Wall | (160,0) | (32,192) | Static | Wall |

Для Mover: GravityScale=0, Fixed Rotation=true, LinearDamping=0;
у обоих коллайдеров Friction=0, Restitution=0, IsTrigger=false.
Настройки доступны в Inspector; имена отдельных полей приведены как в коде.
Подключи следующий класс к Mover через обычную сборку скриптов проекта.
Скрипт предполагает заранее добавленный Rigidbody2D; запускай его только в Play.

```csharp
using System;
using robot2D;

public sealed class PhysicsPractice : Entity
{
    private RigidBody2D body;
    private float elapsed;
    private bool reported;
    private int enters, stays, exits;

    public override void OnCreate()
    {
        body = GetComponent<RigidBody2D>();
        body.LinearVelocity = new Vector2(2f, 0f);
    }

    public override void OnUpdate(float dt)
    {
        elapsed += dt;
        if(!reported && elapsed >= 1f)
        {
            reported = true;
            Console.WriteLine("Position after 1s: " +
                GetComponent<TransformComponent>().Translation.X);
        }
    }

    public override void OnCollisionEnter2D(ulong other, ref PhysicsContact2D contact, Vector2 normalToMe)
    {
        Console.WriteLine("Collision with " + other + ", normal: " + normalToMe.X + ", " + normalToMe.Y);
    }

    public override void OnTriggerEnter2D(ulong other, ref PhysicsContact2D contact)
    {
        ++enters;
        Console.WriteLine("Trigger Enter " + enters);
    }

    public override void OnTriggerStay2D(ulong other, ref PhysicsContact2D contact)
    {
        ++stays; // Count only: avoid printing every physics step.
    }

    public override void OnTriggerExit2D(ulong other, ref PhysicsContact2D contact)
    {
        ++exits;
        Console.WriteLine("Trigger Exit " + exits + ", stays=" + stays);
    }
}
```

Счётчики в этом примере относятся к единственной тестовой паре. Для многих зон
нужно хранить состояние по other/fixture ID. Снимок позиции в OnUpdate берётся
перед очередным Step, поэтому ожидается приблизительное, а не побитовое совпадение.

### 1. Скорость и масштаб

Временно убери Rigidbody/Collider у Wall. При 2 m/s Mover проходит около
64 px за секунду. Поменяй скорость на 4 m/s: ожидается около 128 px/s.
Не умножай скорость на dt. Вопрос для разбора: почему частота отрисовки
не должна менять пройденное за секунду расстояние?
Автоматическая опора: `editor-physics-geometry`, единицы в адаптере.

### 2. Стена и нормаль

Верни Wall и скорость 2 m/s. Mover должен остановиться возле x=128 px
(до левого края стены остаётся его ширина 32 px; допустим небольшой физический зазор).
Ожидается один CollisionEnter. Нормаль к игроку со стены справа направлена влево.
Скорость задаётся один раз в OnCreate: стене разрешено изменить её на столкновении.
Если вместо этого каждый OnUpdate навязывать скорость вправо, получится постоянное
давление на стену — это уже другой игровой контроллер.
Автоматическая опора: `editor-physics-walls` и `editor-physics-bullet`.

### 3. Импульс и масса

Снова убери стену. Замени строку задания скорости в OnCreate на:

```csharp
body.ApplyLinearImpulse(new Vector2(2f, 0f), true);
```

У квадрата 32×32 px площадь 1 m²; при Density=1 и одной фикстуре масса около 1 kg,
поэтому импульс 2 kg*m/s даёт около 2 m/s. При Density=2 ожидается около 1 m/s.
С Damping=0 скорость сохраняется; при положительном LinearDamping уменьшается.
Почему менять трение без контактов недостаточно для такого затухания?
Опыт требует ручной проверки; полной C# регрессии импульса здесь пока нет.

### 4. Полный цикл триггера

Верни Wall, поставь ему IsTrigger=true и Layer=Trigger. Верни задание скорости
в OnCreate. Mover проходит сквозь область: Enter один раз → Stay во время
пересечения → Exit один раз. После выхода счётчики больше не меняются.
На скорости 2 m/s вход ожидается примерно на второй секунде, выход — около третьей.
Поставь скорость -2 m/s и старт справа, чтобы повторить опыт с обратной стороны.
Нормаль и точки sensor не используй для отскока: у него нет твёрдого manifold.
Автоматическая опора: `editor-physics-managed` и `editor-physics-triggers`.

### 5. Фильтрация

Верни IsTrigger=false, Mover оставь Player, Wall временно назначь Projectile.
Default matrix исключает Player/Projectile: Mover проходит без CollisionEnter.
Верни Wall слой Wall: снова появляется твёрдый контакт. При ручной маске
обе стороны должны принимать категорию друг друга. Меняй правила между Play/Stop;
для runtime-изменений native использует markFilterDirty, публичного управления
фильтрами в C# Collider2D пока нет.
Автоматическая опора: `editor-physics-filters`.

## Что можно строить дальше

Для арены сначала достаточно Dynamic игрока/врагов, Static стен,
фильтров и обработки Enter. Урон, принадлежность пули, cooldown и уничтожение
объекта остаются игровыми правилами. Постоянный урон зоны рассчитывай по времени,
а не по количеству Stay. При нескольких контактах одной цели продумай дедупликацию.

Быстрые Dynamic снаряды могут требовать bullet/CCD; это не универсальная
гарантия регистрации быстрого sensor. Для мгновенного оружия или проверки пути
предметно рассмотреть RayCast. World также предлагает QueryAABB — поиск кандидатов
с последующей точной проверкой — и joints. Это возможности Box2D, не обещание
готового C# API robot2D. См. [World](https://box2d.org/doc_version_2_4/classb2_world.html),
[геометрия и запросы](https://box2d.org/doc_version_2_4/md__e_1_2github_2box2d__24_2docs_2collision.html).

При следующем расширении добавляем раздел рядом с соответствующим контрактом,
рабочий пример и проверку; состояние fixed tick сверяем с Core/INPUT/RUNTIME,
не заводим второй конкурирующий план разработки физики.
