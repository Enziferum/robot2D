# Сборка C# и ScriptCore

Первый шаг SCRIPT-01, 2026-10-16. Mono остаётся текущим runtime; переход на
современный .NET, новый hot reload и полная реализация кнопки Build в этот шаг не входят.

## Поддерживаемый путь сборки

`robot2D_ScriptCore` собирает исходники из
`editor/scripting/robot2D-ScriptCore/robot2D-ScriptCore` через найденный Mono mcs.
Профиль — .NET Framework 4.8, язык — C# 7.2; предупреждения компилятора являются
ошибками. Новые `.cs` включаются при следующей сборке через CMake CONFIGURE_DEPENDS,
подкаталоги bin/obj исключены. Исходники C# и пользовательские клипы не попадают в C++.

В проверенной конфигурации Ninja/Release DLL находится в
`<build-dir>/editor/res/script/robot2D_ScriptCore.dll` — это путь загрузки существующего
редактора. Цели `robot2D` и `robot2D-editor-test-suite` зависят от актуального API.
Отдельная команда:

```text
cmake --build <build-dir> --target robot2D_ScriptCore -j 4
```

Правило содержит OUTPUT/DEPENDS: неизменённая DLL не компилируется заново,
изменение исходников или reference DLL вызывает пересборку. Перед компиляцией
удаляется старый выходной DLL-файл; ошибка mcs завершает сборку с ненулевым кодом,
оставляет диагностику компилятора и не выдаёт старую API DLL за новый результат.
Отсутствие mcs диагностируется при конфигурации; путь можно указать через
`-DMONO_MCS_EXECUTABLE=<полный путь>`. Проект Mono находится в исходном репозитории,
в build-каталог попадают только результаты сборки.

Существующий `.csproj` сохранён для IDE/MSBuild. Убрана автоматическая запись в
соседние cmake-build-debug/release. При необходимости копирование DLL задаётся явно:

```text
msbuild robot2D-ScriptCore.csproj /p:Configuration=Release /p:ScriptCoreDeployDirectory=<каталог>
```

CMake и `.csproj` сохраняют имя robot2D_ScriptCore, профиль 4.8 и язык 7.2.
При добавлении файлов нужно сохранять Compile-список старого csproj актуальным.
Независимая версия сборки из AssemblyInfo.cs этим шагом не повышается.

## Проверки и границы

`editor-managed-api` в [suite редактора](editor-testing.md) компилирует C# потребителя
`Entity.GetComponent<Animator>()`, `Play(string)` и `Stop(string)` против свежего
ScriptCore и загружает API под Mono. Это headless-тест загрузки/совместимости
управляемых типов, **не** проверка игровых native callbacks: вызовы анимации без
активной сцены не выполняются. Реализация callbacks относится к ANIM-01.

Python-регрессии `scripts/tests/test_managed_build.py` используют настоящий Mono
и временный CMake-проект: пути с пробелами, отсутствие лишней пересборки, изменение
reference DLL, ошибка исходника, отсутствие старой DLL, восстановление и потеря
выходного файла, отсутствие компилятора. Без CMake/Ninja/Mono они явно пропускаются;
в текущем CI эти инструменты установлены. Изменения собственных `.cs`/`.csproj`
запускают через pre-commit сборку и headless-тесты; clang-tidy не расширяется на C#.

Локально проверены Windows/Mono 6.12, Ninja/Release: редактор, core-tests и suite
собраны, CTest 78/78 без пропусков; Python 47/47. Проверка Mono MSBuild 16.10.1
в этом окружении завершилась MSB6006/csc.exe exit 1 как для нового, так и для
исходного csproj из dev. Поэтому успешная IDE/MSBuild-сборка не заявляется;
подтверждён основной путь CMake/mcs.

На момент первоначального шага SCRIPT-01 оставался открытым: генерация/сборка пользовательского проекта,
диагностика в UI, актуальность сборки при Play и Build, проверка standalone.
Эти ограничения прежнего gen_project.py/EditorLogic устранены следующим шагом
SCRIPT-01 ниже: сборка без shell, явная диагностика и проверка свежей DLL.
Следующий шаг ANIM-01 — безопасное выполнение Play/Stop, выбор именованного клипа,
проверки отсутствующего компонента/клипа и повторного запуска. Граф состояний и
blending не входят в минимум 0.8.


## SCRIPT-01: пользовательский проект и актуальный Play — 2026-10-16

Ветка SCRIPT-01, отдельный worktree script-01, база dev df823bb после merge #120.
По поручению пользователя этот шаг ведёт ассистент; следующие независимые задачи —
HUD-01 и подготовка BUILD-01. Core ECS, fixed tick и игровой Instantiate/Destroy
этим изменением не реализуются.

### Обычный путь автора игры

1. Новый проект получает assets/scripts, GameBootstrap.cs и C# csproj при первой
   сборке. Существующие исходники и IDE project не перезаписываются.
2. Project → Generate Project позволяет выбрать каталог исходников; создаёт
   csproj с относительным References/robot2D_ScriptCore.dll и сразу собирает DLL.
3. Project → Build Scripts запускает фоновую сборку без перехода в Play.
4. Play сначала собирает исходники против свежей ScriptCore. Только успешная
   сборка, загрузка новой DLL и наличие классов сцены разрешают запуск runtime.
   Ошибка оставляет Edit и показывает диалог с диагностикой; полный журнал в Console.
5. Запрос Stop во время ожидающей сборки отменяет последующий автоматический Play.
   Результат старого проекта/сцены не применяется к новому контексту.

C# профиль 4.8 / язык 7.2 / warnings-as-errors сохранён. Источники рекурсивно
берутся из выбранного каталога; bin, obj, References и symlinks исключены.
Модель первого шага — библиотека скриптов с ссылкой на ScriptCore/стандартный SDK;
произвольные пользовательские MSBuild targets, NuGet и другие reference DLL этим
сборщиком не исполняются. Для них потребуется отдельный контракт расширения.

Конфигурация автора — .robot2d/scripts.json в корне проекта (version=1, имя,
путь к исходникам относительно корня). Исполняемая DLL — assets/scripts/bin/<name>.dll.
.robot2d/scripts-build.json публикуется только после успеха. Это новые служебные
файлы сборки, не повышение версии сцен/проектов. Для переноса авторского проекта
нужно переносить также выбранные исходники и .robot2d; если исходники выбраны за
пределами проекта, их относительный путь сам по себе не делает поставку переносимой.

Неуспешная компиляция удаляет прежний выходной DLL-файл/маркер успеха. Старый
скомпилированный проект без исходников не заменяется пустой игрой: его DLL
сохраняется, Play блокируется с просьбой указать C# source project.
После обновления API надо пересобирать пользовательские скрипты.

### Устройство и контракт для Build

editor/res/gen/gen_project.py — общий CLI генерации/сборки. Native ScriptProject
передаёт отдельные аргументы без shell: CreateProcessW с CREATE_NO_WINDOW на Windows,
posix_spawnp на Linux. stdout/stderr захватываются для диагностики. Windows mcs.bat
не запускается через cmd с пользовательскими путями: вызывается Mono + managed mcs.exe.
Response file обходит ограничение длины командной строки; compiler timeout — 120 s.
Для редактора требуются Python 3.8+ и Mono/mcs, обнаруженные при CMake-конфигурации;
отсутствующий инструмент даёт ошибку, а не использование старого результата.

ScriptBuildResult содержит success, путь assembly только при успехе и diagnostic.
Генерация/Build Scripts/Play выполняются задачей TaskQueue; Mono-перезагрузка —
в completion на главном потоке. Открытие/создание проекта пока собирает скрипты
синхронно до десериализации, чтобы были доступны классы. Закрытие редактора может
дождаться компилятора до его timeout; CancellationToken не перерабатывался.

ScriptEngine::runtimeInit теперь возвращает bool. Перезагрузка запрещена при
активном runtime; в Edit старый app domain/metadata освобождаются, ScriptCore и
свежая пользовательская DLL загружаются в новый domain. Это ограниченное обновление
между запусками Play, не live hot reload во время игры. Сохранённые editor-поля
ScriptInteractor не переносятся в новый мир по новому ECS API.

BUILD-01 должен использовать этот же buildProjectScripts и проверять success,
а не самостоятельно выбирать старую DLL по наличию файла. Полноценный ExportTask,
Game.exe, упаковка Mono и standalone относятся к следующим задачам.

### Проверки этого шага

Python: шесть постоянных тестов генератора с настоящим Mono — пути с пробелами/&,
сохранение авторских файлов, новые вложенные исходники, compile error/recovery,
исчезновение compiler/ScriptCore, изменение reference API, защита compiled-only
legacy и некорректные имена. Native suite добавляет editor-script-project,
editor-script-errors и editor-script-reload: настоящий процесс без shell,
диагностика, свежая DLL, Mono-значение 1 → 2 после пересборки, удаление старого
класса и запрет reload при активном runtime.

Редактор/core-tests/editor-test-suite собраны Windows/Ninja/Release; полный
CTest 106/106, включая 41 graphics. Прежние физические/анимационные managed-тесты
сохранены. Изменения генератора включены в native/headless gate обязательного hook.

Ручная приёмка: создать проект в пути с пробелами, Generate, выбрать GameBootstrap;
добавить свой Entity класс и выбрать его в Inspector; Build Scripts; Play/Stop;
испортить .cs и убедиться, что Play остаётся Edit с ошибкой; исправить и повторить.
Затем переименовать используемый класс и проверить диагностику отсутствующего класса.
Эта интерактивная приёмка и готовая Game.exe ещё не выполнялись.
