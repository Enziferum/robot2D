# Диагностика OpenGL и GLSL

Этап RENDER-01 добавляет диагностику к существующему рендеру. Контракт
RenderTarget/RenderWindow, слои, сортировка и batching пока остаются прежними.

## Сообщения во время выполнения

При setup рендера записываются фактические vendor, renderer, OpenGL/GLSL version,
debug-context и ограничения texture units, vertex attributes и color attachments.
Debug-сборка окна запрашивает GLFW debug context; Release сохраняет обычный контекст.
В обычном контексте полнота сообщений драйвера может быть ограничена.

Callback подключается на Windows и Linux при наличии необходимых функций.
Для macOS остаётся проверка glGetError через обёртку. Отсутствие callback
не отключает проверки обёрнутых вызовов.

Сообщение драйвера содержит source, type, severity, id и полный исходный текст.
High отображается как ERROR; medium — ERROR для GL error, WARN для остальных
типов; low — WARN; notification — DEBUG. Сам callback не вызывает OpenGL
и не выпускает исключения через границу драйвера.

`glCall` сохраняет имя операции, C++ файл и строку. При синхронном callback они
также попадают в сообщение драйвера. Для необёрнутых или асинхронных вызовов
место может быть неизвестно. Накопленные до обёртки ошибки выводятся отдельно
как `origin unknown`, а не приписываются следующему корректному вызову.
Обёртка опустошает очередь glGetError; название ошибки сопровождается кратким
объяснением её категории. Это не доказательство конкретной причины ошибки.

После создания RenderWindow можно настроить диагностику при текущем контексте:

```cpp
robot2D::GLDiagnosticsOptions options;
options.synchronous = true;
options.notifications = false;
options.repeatLimit = 3; // 0 — без ограничения повторов
robot2D::configureGLDiagnostics(options);
```

`debugOutput=false` отключает callback текущего контекста, но не glGetError
в обёртках. Фильтр notification и лимит повторов общие для процесса; повторная
настройка сбрасывает счётчики. На последнем разрешённом повторе пишется отметка
о подавлении дальнейших одинаковых сообщений. Учёт ограничен 256 уникальными
сообщениями; при переполнении таблица сбрасывается. Это ограничение объёма лога,
а не точная статистика ошибок за кадр.

GPU shader/program получают имена источников, vertex/index buffers — имена типов.
После успешной линковки выводится `[GLSL] Program linked; program=<ID>;
stage=<stage>; source='<name/path>'`. Так числовой ID из сообщения драйвера
можно сопоставить с программой по тому же логу запуска. Строка появляется при
линковке стадии, а не при каждом use/draw. Имена GUI-источников — ImGui.vertex
и ImGui.fragment. Отрисовка сетки, текста и собственного backend robot2D-imgui
также проходит через glCall, чтобы синхронный callback содержал операцию и C++
file/line. ID действителен только в соответствующем GL-контексте/запуске;
старый ID из прошлого запуска не определяет имя программы в новом.

Предупреждение NVIDIA 131218 о перекомпиляции по GL state сохраняется как
performance/medium, без подавления по ID. Добавленный контекст помогает найти
его источник; сама перекомпиляция этими изменениями не устраняется.

Загрузка VBO сверх capacity или из nullptr при ненулевом размере отклоняется
с указанием buffer ID, requested/capacity в байтах и причины. Исправление
ёмкости CPU/GPU quad-буферов выполнено следующим этапом RENDER-02 и описано
в [проверках batching](render-batching.md).

ShaderHandler различает ошибку чтения файла, пустой источник, ошибку компиляции
и ошибку линковки. Полный driver log читается по GL_INFO_LOG_LENGTH, без лимита
512 символов. Встроенным источникам можно передать четвёртый аргумент sourceName;
при загрузке из файла используется путь. Последняя ошибка доступна через
`getLastError()`; успешное создание стадии её очищает. Существующая поэтапная
сборка программы сохранена; транзакционная замена программы и её владение
будут обсуждаться отдельно вместе с контрактом ресурсов.

## Проверка GLSL без запуска приложения

Нужны Python 3.9+ и [Khronos glslang](https://github.com/KhronosGroup/glslang).
Проверенная версия — **16.6.0**, она закреплена в CI. Утилита называется
glslang; совместимое старое имя — glslangValidator.

```text
python scripts/validate_shaders.py
python scripts/validate_shaders.py --program Core.Quad.430
python scripts/validate_shaders.py --validator C:/tools/glslang.exe --require-version 16.6.0
cmake --build <build-dir> --target robot2D-check-shaders
```

Путь ищется через --validator, затем GLSLANG_VALIDATOR и PATH. CMake-цель
добавляется при найденном Python и не входит в обычную сборку движка.
В CI проверка обязательна на обеих платформах: glslang собирается из тега
16.6.0 с отключёнными SPIR-V/HLSL и собственными тестами.

Манифест [scripts/shaders.json](../scripts/shaders.json) перечисляет программы
и стадии. Сейчас проверяются quad 430/450, текст Core, текст Editor и сетка.
Для встроенного GLSL читается именованный C++ raw string из актуального файла;
для quad добавляется тот же #version, что задаёт runtime. Временные файлы
используются только как вход валидатора, отдельной копии GLSL в репозитории нет.

Каждая стадия проверяется отдельно, затем выполняется -l для проверки связи
стадий. -G/-V не используются: они вводят дополнительные требования SPIR-V.
Синтаксическая ошибка, ошибка связывания, отсутствие инструмента/источника,
неизвестная программа или неверная закреплённая версия возвращают ненулевой код.
Пути и строки сообщений преобразуются обратно к файлу GLSL либо C++ raw string.
Весь непреобразованный текст диагностик также сохраняется в выводе.

Новые файлы GLSL и распознаваемые raw strings с main в собственных core/editor
должны быть зарегистрированы в манифесте, иначе проверка завершится ошибкой.
Это не полноценный парсер C++: конкатенацию строк, макросы и динамические defines
нужно явно поддержать в инструменте при их введении. Проверка исключает extlibs.
При изменении runtime-префиксов quad нужно синхронно обновить варианты манифеста.

Валидатор проверяет язык и связь стадий. Совместимость с конкретным драйвером,
vertex layout, framebuffer attachments и правильность изображения проверяются
отдельно в OpenGL-тестах. Успех glslang не подтверждает эти свойства.

## Регрессии

```text
python -m unittest discover -s scripts/tests -v
ctest --test-dir <build-dir> -R core-graphics- --output-on-failure
```

Две graphics-регрессии находятся в editor/tests/GraphicsDiagnosticsTests.cpp,
связаны только с core и включаются в robot2D-editor-test-suite. Регистрация
требует RB2D_BUILD_EDITOR_TESTS=ON и RB2D_EDITOR_GRAPHICS_TESTS=ON. Нужен настоящий
OpenGL 4.3 debug context; его отсутствие — Skipped (77), а не успех.

Проверяются ошибки обёрток и отсутствие неверной атрибуции старой ошибки,
поля callback, буквальный текст драйвера, фильтр notification, повторы,
отклонение слишком большой загрузки VBO, отсутствующий/пустой/повреждённый
shader, несовместимые стадии и успешная повторная линковка после отказа.
Python-тесты проверяют извлечение, строки исходника, учёт новых GLSL,
отсутствие валидатора, его версию, настоящие синтаксические и link-ошибки.

Для ручной проверки: запустить актуальный Editor, проверить строку OpenGL info,
отображение Scene/Game View и текстовых объектов; открыть Console и убедиться,
что новые сообщения читаются и повторяющиеся ошибки не заполняют лог каждый кадр.
