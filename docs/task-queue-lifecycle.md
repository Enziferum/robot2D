# Завершение фоновых задач

Реализовано 2026-10-15. CancellationToken и проверки токена в конкретных операциях
реализует пользователь; очередь не привязана к типу токена.

## Контракт задачи

- `ITask::requestCancellation() noexcept` — точка подключения токена. Переопределение
  только сигнализирует токен, потокобезопасно и без ожидания worker или вызова
  stop/requestStop/clear очереди. Этот метод может выполняться одновременно с execute.
- В interrupt point внутри execute при обнаружении отмены вызвать `markCancelled()`
  и выйти. Обычный ранний return без этого означает успешное выполнение.
- При обычной ошибке вызвать `fail(message)` и выйти. Необработанное исключение
  перехватывает очередь: исход Failed, описание и exception_ptr сохраняются.
- Если execute вернулся с исходом Pending, очередь назначает Succeeded.
- `getOutcome()`, `getErrorMessage()` и `getException()` читать в callback завершения,
  после выполнения; это не API для опроса изменяемого состояния работающей задачи.
  Для параллельного опроса есть синхронизированные getStatus/getTaskInfo очереди.

Пример подключения будущего токена (имена его методов ещё не навязываются):

```cpp
void MyTask::requestCancellation() noexcept {
    // Запросить отмену через принадлежащее задаче состояние токена.
}

void MyTask::execute() {
    // Выполнить очередную безопасно завершаемую часть работы.
    // Если токен сообщает об отмене:
    // markCancelled();
    // return;
}
```

Обычный callback `addAsyncTask` вызывается только при Succeeded.
`addAsyncTaskWithCompletion` получает также Failed и Cancelled, наблюдённую задачей,
если очередь продолжает работать. Callback вызывается через process на вызывающем
потоке; для приложения это основной поток. Ошибка callback сохраняется в TaskInfo
и логируется, не выходит из process и не останавливает worker.

TaskStatus::Done означает успешное выполнение worker, а не доставленный callback.
hasPendingTasks учитывает вход, активную работу, готовые результаты и выполняемые callbacks.

## Остановка и очистка

requestStop запрещает новые задачи, удаляет ожидающие задачи и готовые результаты,
будит worker и вызывает requestCancellation у текущей задачи. Новые постановки
возвращают InvalidTaskId. Callback, уже взятый process на исполнение, может закончиться.

stop сначала запрашивает остановку, затем синхронизируется с исполнением callback
и делает join без удержания mutex состояния worker. После возврата worker завершён,
принадлежащие очереди задачи и результаты освобождены, новые callbacks не появятся.
Вызов stop из самого callback допустим; из worker нужно вызывать requestStop,
поскольку worker не может сделать join самого себя. Повторный stop допустим.
После остановки очередь не перезапускается.

Без реализации токена выполняющаяся операция доходит до обычного завершения.
Её результат при shutdown отбрасывается и не применяется к UI. Остановка не имеет
гарантированной длительности: блокирующая внешняя операция может задержать join.

clear удаляет ожидающие задачи и готовые результаты, сохраняя работоспособность
очереди. Она не отменяет текущую задачу: её результат позже может быть доставлен.
Для закрытия приложения использовать stop, а не clear. Для отмены при смене
сцены потребуется токен и согласованный контракт области задач.

## Интеграция приложения

При старте EditorModule::setup создаёт ScriptInteractor до ApplicationLogic::setup,
который может начать автозагрузку проекта.

При штатном завершении EditorLogic ждёт остановки очереди, затем завершает runtime.
Application освобождает EditorModule при живом Mono. Shutdown scripting останавливает
file watcher, освобождает scripting-ссылки и завершает Mono. Engine освобождает
Application и её GUI до уничтожения локального окна.

Ошибки SceneLoadTask больше не публикуют новую активную сцену. При неудачной смене
сохраняется предыдущая сцена; при неудачном первом открытии показан LoadFailed
с указанием на лог. Автоматический возврат в браузер проектов и повтор загрузки
из этого экрана пока не реализованы. Поколение запроса SceneManager защищает от
применения устаревшей загрузки сцены; оно не заменяет отмену сторонних asset-задач.

Аварийный cleanup после исключения в середине setup и владение глобальными
графическими кэшами требуют отдельной проработки; этот шаг исправляет штатный путь.

## Проверки

CTest без нового тестового фреймворка, включение опцией RB2D_BUILD_EDITOR_TESTS:

```text
cmake -S . -B cmake-build-debug -DRB2D_BUILD_EDITOR_TESTS=ON
cmake --build cmake-build-debug --target robot2D-task-tests robot2D -j 4
ctest --test-dir cmake-build-debug/editor/tests --output-on-failure
```

Шесть сценариев прошли: пустая/повторная остановка, исходы и исключение worker,
ожидающие задачи и сигнал активной, очистка всех результатов, ошибка callback и
stop внутри него, ожидание уже начавшегося callback. Редактор собран.

Ручная проверка ещё нужна: автооткрытие последнего проекта, повреждённая сцена,
неудачная смена с сохранением текущей сцены, закрытие во время загрузки и runtime.
