# Prefab 0.8: файл и независимые экземпляры

Шаблон — `.prefab` в `assets/` проекта, содержащий одно дерево сущностей.
Существующий формат PrefabVersion 1 сохранён. Варианты, вложенные overrides и
автоматическое распространение изменений не входят в PREFAB-01.

## Сохранение и использование в редакторе

1. Создать корень врага или пули и его дочерние сущности. Ресурсы импортировать
   в `assets/`; ссылки Entity/Transform и Button должны вести внутрь этого дерева
   либо быть пустыми. Внешние ссылки отклоняются при сохранении и загрузке prefab.
2. Перетащить корень из Scene в каталог Assets: создаётся `<имя>.prefab`.
   Существующий файл не перезаписывается этим действием; изменение шаблона
   сохраняется через Save в редакторе prefab.
3. Перетащить файл из Assets в Scene или Viewport. Создаётся новое дерево,
   в Viewport его корень выделяется; исходный шаблон остаётся отдельным объектом.
   Вставка использует позицию из шаблона, позиционирование в точке мыши не добавлено.
4. Повторить вставку, изменить один экземпляр, сохранить и переоткрыть сцену.
   Экземпляры сохраняются как обычные деревья компонентов с меткой PrefabUUID.
   Эта метка идентифицирует asset; она не является UUID экземпляра.

Перетаскивание prefab в существующее поле C# типа Entity по-прежнему создаёт
сценовую копию для этого поля. Для будущего спавна следует использовать файловый
путь шаблона; поле Entity не является ссылкой на prefab asset.

## Native-контракт для runtime

```cpp
editor::PrefabManager library;
auto prefab = library.loadPrefab(projectPath, "assets/enemies/enemy.prefab", scripts);
if(prefab) {
    auto instance = targetScene.instantiateTemplate(prefab -> getEntity(), scripts);
    // instance содержит данные; runtime caller выполняет активацию ниже.
}
```

Загрузчик не требует UIInteractor, привязки к выбранной сущности или скрытых
копий будущих врагов в игровой сцене. Относительный путь разрешается от корня
проекта, а не cwd. Выход за `assets/`, неверное расширение и невалидный файл
возвращают nullptr с диагностикой пути и причины; неуспешная загрузка не кэшируется.
Успешный шаблон владеет отдельной Scene. Кэш использует тот же script interactor,
который хранит поля шаблона; interactor должен жить и использоваться при создании
экземпляров. Смена проекта/interactor требует новой библиотеки шаблонов.

`Scene::instantiateTemplate` создаёт данные в текущем контексте Scene: Editor
до Play, Runtime во время Play. Каждому узлу выдаётся новый ненулевой UUID,
иерархия и внутренние ссылки Button/Entity/Transform переназначаются в два прохода.
Компоненты и поля независимы; текстуры/шрифты могут разделять ресурс кэша.
Не копируются QuadTree, callback кнопки, runtimeBody/runtimeFixture и состояние
Animator. Определения анимаций копируются под UUID нового владельца.
При отсутствии требуемого script interactor или внешних ссылках чужого дерева
вставка отклоняется до создания сущностей. Пустой результат обозначает отказ.
Гарантия отката при исключении выделения памяти не добавлена.

Это фабрика данных для RUNTIME-01, а не реализация C# игрового спавна.
Runtime caller должен в безопасной точке кадра подготовить GPU-ресурсы, создать
physics bodies/fixtures и managed instances, зарегистрировать UI callbacks,
вызвать OnCreate после связывания всех сущностей и включить их в обновление.
Вызов из physics callback, Destroy и жизнь возвращённого C# Entity определяются
RUNTIME-01/PHYS-01. Новый C# API в этом шаге не добавляется.
После Stop дескрипторы созданных Runtime-сущностей становятся недействительными;
редакторское дерево и dirty-state не меняются. `duplicateEmptyEntity` сохраняет
прежнее ограничение Editor-only и использует ту же фабрику.

## Ресурсы и Build

Переносимые ссылки на изображения, шрифты и XML-клипы следуют
[контракту ресурсов](project-assets.md). Отсутствующий ресурс пока диагностируется
загрузчиком CPU и не превращает prefab в полноценный проверенный игровой пакет.
`copyProjectAssets(projectPath, destinationRoot)` сохраняет весь `assets`, включая
prefab, клипы и их изображения; вырезать якобы неиспользуемые prefab нельзя,
поскольку игровой код сможет ссылаться на путь без сценового экземпляра.

Регрессия переносит настоящий prefab + XML + TGA в другую папку, переименовывает
исходный `assets`, загружает шаблон по тому же относительному пути и создаёт
экземпляр из пакета. Это проверка native-упаковки assets. ExportTask остаётся
заглушкой; кнопка Build, Game.exe и запуск готовой игры относятся к BUILD-01 и
PLAYER-01 и пока не проверены. PREFAB-01 остаётся открытой до этой интеграции.

## Проверки

`robot2D-prefab-tests` включён в `robot2D-editor-test-suite`; четыре headless
сценария `editor-prefab-instances/invalid/runtime/package` проверяют файловый путь,
UUID, remap ссылок, независимость компонентов/полей, повторный Play/Stop,
отказ без изменения целевой сцены и перенос пакета. `editor-scene-prefab-viewport`
в graphics suite проверяет реальное сообщение вставки, дерево, QuadTree,
выделение и ошибку отсутствующего файла.

Ручная приёмка: создать Enemy с дочерним Weapon и внутренними ссылками, сохранить
в Assets, удалить исходный сценовый объект; вставить файл по два раза через Scene
и Viewport, изменить первый экземпляр, сохранить и открыть сцену снова. Проверить
независимость второго экземпляра и шаблона, выбор/перемещение дочерних узлов.
Отдельно проверить отклонение ссылки на сущность вне дерева. Ручное перетаскивание
и реальная игровая/standalone-приёмка автоматическими тестами не заменяются.
