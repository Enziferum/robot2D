# Работа над robot2D

## Начало и завершение задачи

- Перед изменением файлов проверь `git status` и актуальный код затронутой области; для работы по задаче сверь соответствующую Issue. [Общий план](docs/project-roadmap.md) используй для приоритетов и межмодульных зависимостей, [релизный маршрут](docs/release-roadmap.md) — для критериев релиза, [историю редактора](docs/editor-roadmap.md) — при необходимости исторического контекста. Читай относящиеся к задаче разделы; уже изученное перечитывай при изменениях или конкретной неопределённости.
- Объём исследования, реализации, документации и проверок должен соответствовать сложности и риску изменения. Для небольшой правки не создавай отдельный план, документ, Issue или ветку только ради процесса; существующую задачу и worktree переиспользуй, когда это уместно. Для нетривиальной реализации кратко определи результат и критерии готовности; расширяй область работы при обнаружении существенной зависимости или по запросу пользователя.
- Работай в границах запрошенной задачи. Обсуждение и ревью сами по себе не являются запросом менять код. Внутри согласованной реализации выполняй обычные действия самостоятельно.
- Сохраняй незавершённые изменения пользователя. Не добавляй соседний рефакторинг и массовое форматирование к функциональной задаче.
- При параллельной реализации используй отдельный Git worktree; сначала проверь существующие и переиспользуй подходящий. Правила веток и PR приведены ниже. Основной checkout пользователя под IDE не переключай, его файлы, индекс и конфигурацию сборки не меняй без явного поручения. Сборку и проверки выполняй в своём worktree. Ограничения среды и разрешения на команды соблюдай.
- После реализации фиксируй результат, проверки, ограничения и следующий шаг в связанной задаче; roadmap обновляй при изменении маршрута, статуса этапа или межмодульных договорённостей. Не дублируй подробный отчёт во всех документах. Новую внеплановую работу предлагай отдельно.
- При передаче изменений на ревью всегда выдавай в чате список изменённых файлов в порядке приоритета просмотра: внимательно разобрать, проверить функционально, достаточно быстрого просмотра. Для каждого файла или связной группы указывай причину приоритета и что именно проверить; небольшие изменения с большим влиянием выделяй отдельно. Опирайся на актуальный diff, а не на число строк; тесты связывай с проверяемой реализацией, ресурсы и механические изменения группируй. Для маленькой правки достаточно короткого списка без пустых категорий. При изменении состава PR актуализируй список; подготовка списка сама по себе не требует отдельной ветки или документа.
- Не используй computer-use и автоматическое управление интерфейсом robot2D. Пользователь проверяет UI сам и предоставляет скриншоты; ассистент работает с кодом, логами, сборкой и автоматическими тестами.
- Общайся по-русски. Объясняй существенные решения и компромиссы; различай подтверждённые требования и предложения.

## Карта проекта

- `core/` — библиотека движка; `core/tests/` — тесты ядра на GoogleTest; `core/sandbox/` — эксперименты.
- `editor/include/editor/` и `editor/src/` — интерфейсы и реализация редактора; `editor/res/` — его ресурсы.
- `editor/extlibs/` — зависимости, в том числе собственные библиотеки. Перед правкой проверь происхождение и способ подключения: yaml-cpp, box2d и RBIni зарегистрированы как submodules в `.gitmodules`.
- `cmake/`, `core/cmake/`, `editor/cmake/` — настройки сборки. Актуальные имена целей и опций проверяй здесь, поскольку README может отставать.
- `work/` игнорируется Git: подходит для временных логов и экспериментов. Постоянные тесты, решения и инструкции храни в отслеживаемых файлах.

## C++ и проверка

- Проект использует C++17 и CMake 3.21+. Стиль: 4 пробела, отступ внутри namespace, скобка на той же строке, `T*`/`T&` рядом с типом, `if(...)` и `object -> method()`. Порядок include сохраняем. Конфигурация — `uncrustify.cfg`; массовое форматирование выполняй отдельной задачей.
- Сборка выполняется вне дерева исходников. Используй подходящий существующий build-каталог; перед конфигурацией проверь его генератор, компилятор и опции. Не перенастраивай рабочую конфигурацию CLion ради отдельной проверки.
- Цели: `robot2D` — редактор, `robot2D-core` — библиотека, `robot2D-core-tests` — тесты ядра при `RB2D_BUILD_CORE_TESTS=ON`.
- Примеры команд, где `<build-dir>` — проверенный каталог сборки:

  ```text
  cmake --build <build-dir> --target robot2D -j 4
  cmake --build <build-dir> --target robot2D-core-tests -j 4
  ctest --test-dir <build-dir>/core/tests --output-on-failure
  ```

- При изменении поведения добавляй проверки наблюдаемого результата, значимых граничных случаев и регрессий, когда это практически оправдано. Используй существующую инфраструктуру; для UI описывай конкретный ручной сценарий.
- Постоянные тесты редактора — `editor/tests/`, запуск и разделение headless/graphics описаны в [инструкции](docs/editor-testing.md). Включение: `RB2D_BUILD_EDITOR_TESTS=ON`, цель `robot2D-editor-test-suite`; graphics регистрируются отдельно через `RB2D_EDITOR_GRAPHICS_TESTS=ON`. Не подменяй запуск suite временными тестами из work.
- Успешная компиляция отдельного файла или временный smoke-test не означают, что редактор собран и проверен целиком. Указывай, что запускалось, результат и причины незапущенных проверок.
- При изменениях только документации проверь ссылки и diff; сборка не требуется.
- Выбирай проверки по затронутому поведению и риску. После успешных обязательных и относящихся к изменению проверок завершай работу. Повторный или более широкий прогон нужен при новых изменениях, сбое, изменении значимого окружения либо конкретной непроверенной гипотезе; указывай причину. Учитывай проверки обязательного hook, чтобы без необходимости не дублировать их вручную. Результаты относятся к проверенной версии кода и окружению: не выдавай прежний запуск за новый и не распространяй его на непроверенные изменения. Это правило не разрешает пропускать обязательные hooks.
- Для запуска анализатора и форматтера прочитай [инструкцию по инструментам](docs/development-tools.md). Не используй clang-format для этих исходников: проверенная версия удаляет выбранные пользователем пробелы вокруг `->`.
- clang-tidy запускай через `scripts/run_clang_tidy.ps1`: по умолчанию только собственный код core/editor. Код extlibs проверяй только по явному запросу пользователя, с `-Scope` на указанную библиотеку, подкаталог или файл; не расширяй такой запуск на остальные зависимости.
- Обязательные pre-commit и commit-msg hooks не отключай и не обходи. Pre-commit проверяет формат изменённых собственных C++ файлов целиком, затем сборку, headless-тесты и строгий clang-tidy; изменения настроек запускают полный анализ. После clone установи hooks через `scripts/install_git_hooks.py`; настройка инструментов и выделенного Ninja/Release каталога описана в [инструкции](docs/development-tools.md). Чужие stb/glad/Khronos в Graphics/internal исключены из стандартной области, как и extlibs.
- Добавляя диагностические логи, фиксируй границы операций, путь/ID и причину ошибки. Избегай сообщений INFO на каждом кадре. Правила уровней и разбор границ классов — в [архитектурном разборе](docs/application-architecture-review.md); предложения оттуда не являются разрешением на рефакторинг.

## Где хранить контекст

- До изменения общего API сверяй связанные Issues, договорённости и потребителей. Не заводи конкурирующий план в отдельном чате и не считай чужую задачу завершённой по предположению.

- Релизный маршрут 0.8–1.0, зависимости и формат совместной работы — [release-roadmap.md](docs/release-roadmap.md). Ведущий совместной задачи выбирается перед стартом: пользователь развивает собственные навыки и может брать сложные задачи движка. Не подменяй выбранную помощь/ревью самостоятельной реализацией. Snapshot и CancellationToken остаются за пользователем.

- Версия core/editor задаётся только в корневом `project(robot2D VERSION ...)`; C++ получает сгенерированный Version.hpp. Канал, Git SHA, release-теги и независимые версии файлов — в `docs/versioning.md`. Не дублируй номер версии в исходниках и не повышай схемы файлов из-за повышения версии приложения.

- Учёт задач и коммиты: [правила проекта](docs/project-workflow.md). Первая строка коммита — `TASK-ID: описание`, ID должен быть зарегистрирован в `.github/tasks.json`.
- Issues и Projects создавай и изменяй через GitHub CLI (`gh`), без автоматизации браузера. Доска, репозиторий и соответствие ID → Issue указаны в `.github/tasks.json`. Перед созданием проверяй существующие Issues, чтобы не делать дубликаты. Авторизация браузера допустима только как часть входа самого gh; токены в чат/репозиторий не выводи.
- Основная интеграционная ветка — `dev`. Новую рабочую ветку создавай от актуального удалённого `dev` без префикса `codex/`: `TASK-ID` или `TASK-ID-описание` (например `ASSET-02` или `CI-01-pr-only`). Сначала проверь связанные ветки; связь Development создавай через `gh issue develop --base dev`, PR задач направляй в `dev`. Явное поручение пользователя работать в текущей ветке или продолжить общую интеграцию задаёт исключение и не требует новой ветки. `october2026_dev` слита через PR #43 и больше не используется как база новых задач. `release/0.8.0` создаётся от `dev` ближе к стабилизации, выпуск фиксируется тегом `v0.8.0`. Метки задач заданы в `.github/task-labels.json`; предварительный просмотр/назначение — `scripts/sync_task_labels.ps1` и `-Apply`. Правила — docs/project-workflow.md.

- GitHub Issues/Projects — оперативные статусы; `docs/project-roadmap.md` — общий маршрут и синхронизация направлений, `docs/release-roadmap.md` — релизные критерии, `docs/editor-roadmap.md` — история редактора и датированные результаты. ID и ссылки на Issues — `.github/tasks.json`. Core-задачи ведутся в тех же milestones/Projects с меткой area:core; рендер дополнительно получает area:render.
- Долговременные архитектурные договорённости записывай в документацию рядом с кодом или в `docs/`, когда они согласованы и проверены по реализации; не превращай предположения в ограничения.
- Skills используй для повторяемых процедур с собственными шагами и ресурсами. Текущие приоритеты, конкретные баги и статусы в skills не помещай. Доступный `robot2d-collaborator` дополняет эти правила; работа с репозиторием должна быть понятна и без его установки.
