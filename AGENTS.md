# Работа над robot2D

## Начало и завершение задачи

- Перед работой прочитай [план редактора](docs/editor-roadmap.md), затем проверь актуальный код и `git status`. Состояние в переписке и roadmap сверяй с файлами; не объявляй прошлые проверки выполненными заново.
- Работай в границах запрошенной задачи. Обсуждение и ревью сами по себе не являются запросом менять код. Внутри согласованной реализации выполняй обычные действия самостоятельно.
- Сохраняй незавершённые изменения пользователя. Не добавляй соседний рефакторинг и массовое форматирование к функциональной задаче.
- После реализации обновляй связанную задачу в roadmap: результат, проверки, ограничения и следующий шаг. Новую внеплановую работу предлагай отдельно.
- Общайся по-русски. Объясняй существенные решения и компромиссы; различай подтверждённые требования и предложения.

## Карта проекта

- `core/` — библиотека движка; `core/tests/` — тесты ядра на GoogleTest; `core/sandbox/` — эксперименты.
- `editor/include/editor/` и `editor/src/` — интерфейсы и реализация редактора; `editor/res/` — его ресурсы.
- `editor/extlibs/` — зависимости, в том числе собственные библиотеки. Перед правкой проверь происхождение и способ подключения: yaml-cpp, box2d и RBIni зарегистрированы как submodules в `.gitmodules`.
- `cmake/`, `core/cmake/`, `editor/cmake/` — настройки сборки. Актуальные имена целей и опций проверяй здесь, поскольку README может отставать.
- `work/` игнорируется Git: подходит для временных логов и экспериментов. Постоянные тесты, решения и инструкции храни в отслеживаемых файлах.

## C++ и проверка

- Проект использует C++17 и CMake 3.21+. Стиль: 4 пробела, отступ внутри namespace, скобка на той же строке, `T*`/`T&` рядом с типом, `if(...)` и `object -> method()`. Порядок include сохраняем. Конфигурация — `uncrustify.cfg`; массовое форматирование выполняй отдельной задачей.
- Сборка выполняется вне дерева исходников. Используй подходящий существующий build-каталог; перед конфигурацией проверь его генератор, компилятор и опции. Не перенастраивай рабочую конфигурацию CLion ради отдельной проверки.
- Цели: `robot2D` — редактор, `robot2D-core` — библиотека, `robot2D-core-tests` — тесты ядра при `RB2D_BUILD_CORE_TESTS=ON`.
- Примеры команд, где `<build-dir>` — проверенный каталог сборки:

  ```text
  cmake --build <build-dir> --target robot2D -j 4
  cmake --build <build-dir> --target robot2D-core-tests -j 4
  ctest --test-dir <build-dir>/core/tests --output-on-failure
  ```

- При изменении поведения добавляй проверки наблюдаемого результата, значимых граничных случаев и регрессий, когда это практически оправдано. Используй существующую инфраструктуру; для UI описывай конкретный ручной сценарий.
- Постоянные тесты редактора — `editor/tests/`, запуск и разделение headless/graphics описаны в [инструкции](docs/editor-testing.md). Включение: `RB2D_BUILD_EDITOR_TESTS=ON`, цель `robot2D-editor-test-suite`; graphics регистрируются отдельно через `RB2D_EDITOR_GRAPHICS_TESTS=ON`. Не подменяй запуск suite временными тестами из work.
- Успешная компиляция отдельного файла или временный smoke-test не означают, что редактор собран и проверен целиком. Указывай, что запускалось, результат и причины незапущенных проверок.
- При изменениях только документации проверь ссылки и diff; сборка не требуется.
- Для запуска анализатора и форматтера прочитай [инструкцию по инструментам](docs/development-tools.md). Не используй clang-format для этих исходников: проверенная версия удаляет выбранные пользователем пробелы вокруг `->`.
- clang-tidy запускай через `scripts/run_clang_tidy.ps1`: по умолчанию только собственный код core/editor. Код extlibs проверяй только по явному запросу пользователя, с `-Scope` на указанную библиотеку, подкаталог или файл; не расширяй такой запуск на остальные зависимости.
- Pre-commit проверяет формат изменённых собственных C++ файлов целиком, затем сборку, headless-тесты и строгий clang-tidy; изменения настроек запускают полный анализ. Не обходи hook. Инструменты и выделенный Ninja/Release каталог настраиваются через `scripts/install_git_hooks.py`, детали — в `docs/development-tools.md`. Чужие stb/glad/Khronos в Graphics/internal исключены из стандартной области, как и extlibs.
- Добавляя диагностические логи, фиксируй границы операций, путь/ID и причину ошибки. Избегай сообщений INFO на каждом кадре. Правила уровней и разбор границ классов — в [архитектурном разборе](docs/application-architecture-review.md); предложения оттуда не являются разрешением на рефакторинг.

## Где хранить контекст

- Версия core/editor задаётся только в корневом `project(robot2D VERSION ...)`; C++ получает сгенерированный Version.hpp. Канал, Git SHA, release-теги и независимые версии файлов — в `docs/versioning.md`. Не дублируй номер версии в исходниках и не повышай схемы файлов из-за повышения версии приложения.

- Учёт задач и коммиты: [правила проекта](docs/project-workflow.md). Первая строка коммита — `TASK-ID: описание`, ID должен быть зарегистрирован в `.github/tasks.json`. После clone включи проверку через `python scripts/install_git_hooks.py`; не обходи hook ради коммита без ID.
- Issues и Projects создавай и изменяй через GitHub CLI (`gh`), без автоматизации браузера. Доска, репозиторий и соответствие ID → Issue указаны в `.github/tasks.json`. Перед созданием проверяй существующие Issues, чтобы не делать дубликаты. Авторизация браузера допустима только как часть входа самого gh; токены в чат/репозиторий не выводи.
- Для новой рабочей ветки используй `codex/<task-id>-<описание>` и связь Development через `gh issue develop` с явно выбранной удалённой базой. Сначала проверь связанные ветки. Метки задач заданы в `.github/task-labels.json`; предварительный просмотр/назначение — `scripts/sync_task_labels.ps1` и `-Apply`. Правила — docs/project-workflow.md.

- Этот файл — постоянные правила и указатели на документацию проекта.
- GitHub Issues/Projects — оперативные статусы; `docs/editor-roadmap.md` — план, ответственность, датированные результаты проверок и передача контекста между чатами. ID и ссылки на Issues — `.github/tasks.json`.
- Долговременные архитектурные договорённости записывай в документацию рядом с кодом или в `docs/`, когда они согласованы и проверены по реализации; не превращай предположения в ограничения.
- Skills используй для повторяемых процедур с собственными шагами и ресурсами. Текущие приоритеты, конкретные баги и статусы в skills не помещай. Доступный `robot2d-collaborator` дополняет эти правила; работа с репозиторием должна быть понятна и без его установки.
