# Работа над robot2D

## Область работы

- Перед изменениями проверь `git status`, затронутый код и связанную Issue. Сохраняй незавершённые изменения пользователя. Обсуждение и ревью не разрешают реализацию без поручения.
- Объём исследования, документации и проверок выбирай по сложности и риску задачи. Читай нужные разделы; перечитывай при изменениях или конкретной неопределённости. Для небольшой правки не создавай план, документ, Issue или ветку только ради процесса. Не добавляй соседний рефакторинг и массовое форматирование.
- При параллельной реализации переиспользуй подходящий отдельный worktree. Основной checkout IDE, его индекс и конфигурацию сборки не меняй без явного поручения.
- Существенные контракты сверяй с публичными интерфейсами, потребителями и тестами. Оперативные задачи и критерии готовности ведутся в GitHub Issues/Projects; соответствие TASK-ID и Issue — в `.github/tasks.json`. Не считай чужую работу завершённой без подтверждения.
- После шага кратко фиксируй результат, проверки, ограничения и следующий шаг в связанной задаче, когда это необходимо для продолжения работы. Не дублируй отчёты в нескольких местах. Внутренние планы, журналы работы и обсуждения не добавляй в публичный репозиторий; пользовательские руководства находятся на [сайте](https://enziferum.github.io/robot2D/docs/).
- Передавая работу на ревью, выдавай в чате список файлов по приоритету просмотра: внимательно, функционально, быстро. Объясняй, что проверить и почему; выделяй маленькие изменения с большим влиянием. Тесты связывай с реализацией, ресурсы и механические изменения группируй. Для маленькой правки достаточно короткого списка. Список основывай на актуальном diff и обновляй при изменении PR.
- Общайся по-русски, различай требования, подтверждённые результаты и предложения. Не используй computer-use и автоматическое управление UI robot2D; UI/игровая приёмка выполняется вручную.

## Карта проекта

- `core/` — библиотека движка; `core/tests/` — GoogleTest; `core/sandbox/` — эксперименты.
- `editor/include/editor/`, `editor/src/`, `editor/res/`, `editor/tests/` — редактор, ресурсы и постоянные тесты.
- `editor/scripting/` — C# API; `examples/` — проекты игр; `website/` — публичные руководства и примеры Core.
- `cmake/`, `core/cmake/`, `editor/cmake/` — настройки сборки; актуальные цели и опции проверяй здесь.
- До изменения зависимостей проверь происхождение и подключение. yaml-cpp, Box2D и RBIni — submodules в `.gitmodules`.
- `work/` игнорируется Git: временные логи, локальные внутренние материалы и эксперименты. Нужные сборке файлы, регрессионные тесты и пользовательские инструкции должны оставаться отслеживаемыми.

## Код и проверка

- C++17, CMake 3.21+. Стиль: 4 пробела, отступ внутри namespace, скобка на той же строке, `T*`/`T&`, `if(...)`, `object -> method()`. Сохраняй порядок include. Формат — `uncrustify.cfg`; clang-format не используй: он меняет согласованные пробелы вокруг `->`.
- Используй отдельный подходящий build-каталог. Перед конфигурацией проверь генератор, компилятор и опции в CMakeCache.txt; конфигурацию CLion для отдельной проверки не перенастраивай.
- Цели: `robot2D` — редактор, `robot2D-core` — библиотека, `robot2D-player` — standalone player. Тесты ядра: `RB2D_BUILD_CORE_TESTS=ON`, цель `robot2D-core-tests`; редактора: `RB2D_BUILD_EDITOR_TESTS=ON`, цель `robot2D-editor-test-suite`. Graphics включаются отдельно: `RB2D_EDITOR_GRAPHICS_TESTS=ON`. Не подменяй suite временными smoke-тестами.

```text
cmake --build <build-dir> --target robot2D robot2D-core-tests robot2D-editor-test-suite -j 4
ctest --test-dir <build-dir> --output-on-failure --no-tests=error
```

- Добавляй проверки наблюдаемого поведения и значимых регрессий, когда это оправдано. Для UI указывай ручной сценарий. Сообщай, что реально запускалось и что осталось непроверенным: компиляция файла или smoke не означают полную приёмку.
- После успешных обязательных и относящихся к изменению проверок завершай работу. Повторный или более широкий прогон нужен при новых изменениях, сбое, изменении значимого окружения или конкретной непроверенной гипотезе; указывай причину. Учитывай запуск hook, чтобы без необходимости не дублировать его вручную. Результаты относятся к проверенной версии и окружению; прежний запуск не выдавай за новый. Для документации достаточно diff и проверки ссылок.
- Обязательные pre-commit и commit-msg hooks не отключай и не обходи. После clone запусти `python scripts/install_git_hooks.py`; пути инструментов и выделенный Ninja/Release build задаются параметрами `--uncrustify`, `--clang-tidy`, `--build-dir`, `--jobs`. Нужны Uncrustify 0.83.0, clang-tidy, PowerShell 7, CMake, Ninja и зависимости сборки. Настройки Git общие для worktrees: не указывай сборку CLion. План hook: `python scripts/pre_commit.py --plan`.
- Pre-commit проверяет Python-регрессии, формат изменённых собственных C++ файлов целиком, сборку, headless-тесты и строгий clang-tidy. Анализируется затронутый C++ код; изменения сборочных/аналитических настроек запускают полный анализ. C# изменения проверяются сборкой и headless-тестами, Python — Python-регрессиями. Частично staged исходники и настройки не допускаются; hook ничего не исправляет автоматически.
- Анализатор запускай через `scripts/run_clang_tidy.ps1 -BuildDirectory <build-dir> -WarningsAsErrors`. По умолчанию только собственный код core/editor; extlibs/ext и скопированные stb/glad/Khronos исключены. Зависимости проверяй только по явному запросу с конкретным `-Scope`.
- Логи фиксируют границы операций, путь/ID и причину ошибки; избегай INFO на каждом кадре.
- Версия core/editor задаётся только в корневом `project(robot2D VERSION ...)`; `cmake/Version.cmake` генерирует Version.hpp. Не дублируй номер в исходниках и не меняй версии файловых схем из-за версии приложения.

## Git и ревью

- Сообщение коммита: `TASK-ID: описание`; ID зарегистрирован в `.github/tasks.json`.
- Основная интеграционная ветка — `dev`. Новые рабочие ветки создавай от актуального удалённого `dev`: `TASK-ID` или `TASK-ID-описание`, без `codex/`. Сначала проверь связанные ветки; Development связывай через `gh issue develop --base dev`; PR направляй в `dev`. Явное поручение продолжить текущую ветку или общую интеграцию — исключение, новая ветка не нужна. Обычный push рабочих веток разрешён; force-push и прямая запись в dev требуют подтверждения.
- Issues/Projects изменяй через `gh`, без автоматизации браузера; перед созданием проверь существующие задачи. `Refs #N` — для незавершённого шага, `Closes #N` — только при выполнении критериев. Токены не выводи в чат или репозиторий. Метки: `.github/task-labels.json`, предварительный просмотр: `scripts/sync_task_labels.ps1`, применение: `-Apply`.
- Ревью по запросу: `scripts/review.ps1` либо `scripts/review.py`; можно ограничить `-Files`/`--files`, подготовить материалы без модели через `-PrepareOnly`/`--prepare-only`. Ревьюер по умолчанию только читает: не меняет исходники, Git и статусы. Проверяй версию и область отчёта, обосновывай ошибки условием возникновения и последствиями, отделяй вопросы и предложения. Не придумывай замечания ради количества. Проверки сборкой разрешаются отдельно через `-RunChecks`/`--run-checks` с существующим build-каталогом.
- Skills дополняют эти правила повторяемыми процедурами; статусы задач и внутреннюю историю в skills не помещай.
